## Design system

- **`DESIGN.md`** (racine du repo) est la référence **unique** pour les couleurs, la nomenclature M3 et les ratios WCAG déjà vérifiés. Le consulter avant tout changement de `src/styles.css` ou de token. Règle permanente : toute session qui touche le design system met à jour `DESIGN.md` dans la foulée, pas seulement sur demande.
- Tokens définis **uniquement** dans `src/styles.css` (`@theme inline` + `:root`/`.dark`/`:root:not(.dark)`). Pas de `tailwind.config.*` (Tailwind v4, CSS-first).
- `src/components/ui/` (shadcn) = code mort confirmé, ne pas modifier sans demande explicite de le réactiver.
- **Icônes** : Lucide uniquement (`lucide-react`), jamais Material Symbols. Règle globale `styles.css` (`@layer base`) : `.lucide { stroke-width: 1.5 }` (uniforme, plus d'exception sous 16px) + `cursor: pointer` systématique sur `button`/`[role="button"]`/`a[href]`/`select`/`label[for]`/checkbox/radio. **Exception explicite (14/07)** : `react-icons/fa6` (`FaLinkedin`/`FaXTwitter`) pour les 2 logos de marque du profil public — Lucide n'a pas de vrai logo X/LinkedIn. Ne pas généraliser au-delà de ce cas.
- **Nav admin** (`AdminSidebar`, `AdminPage.tsx`) : couleur par section via `NAV_ACTIVE_CLASSES`, détail complet (valeurs, ratios) dans `DESIGN.md` section "Couleurs de nav active + badges". Les halos `SectionAurora` de chaque section sont volontairement dissociés de cette couleur de nav depuis le 13/07 — ne pas chercher à les réaligner (exception : Paramètres, dont le nav + halo ont été réalignés sur `teal` le 14/07 pour matcher Vue d'ensemble, sur demande explicite). Les cartes "accès rapide" du Dashboard (`QuickAccessCard`) reprennent elles aussi la couleur nav de leur onglet cible, pas une teinte partagée — depuis le 17/07, `QuickAccessCard` a deux dispositions distinctes (`md:hidden`/`hidden md:flex`, mobile vs desktop, cf. `DESIGN.md` section "Navigation mobile"), toucher une seule des deux sans vérifier l'autre est une régression facile. `AdminSidebar` elle-même est cachée sur mobile (`hidden md:flex`), remplacée par `AdminMobileBottomNav`.
- **Filtres admin** : `AdminFilterBar` (`src/components/AdminFilterBar.tsx`) est le composant de référence pour tout filtre côté dashboard admin (Projets/Demandes/Contacts/Veille + les listes Vue d'ensemble) — reprend le shell visuel du bouton "Filtrer" de `FilterBar.tsx` (catalogue public) mais généralisé à des groupes arbitraires. Ne pas recréer de pills ad hoc (`veillePillCls` encore présent uniquement pour le filtre mois de la mini-table Veille du Dashboard, cas non couvert par `AdminFilterBar`).
- **Tooltips** : `TooltipProvider` (Radix, `src/components/ui/tooltip.tsx`) actif globalement depuis `RootLayout.tsx` (14/07 — auparavant quasi inutilisé). Tout bouton icône-seul (sans texte visible) doit être enveloppé dans `IconTooltip` (`src/components/IconTooltip.tsx`, reprend le libellé `aria-label` existant).
- **⚠️ Divergence non résolue** : `secondary` vaut `#7c3aed` dans `styles.css` (dark) mais `DESIGN.md` liste `#D2BBFF` — à trancher avec l'utilisatrice avant la passe light mode, ne pas corriger à l'aveugle.
- **Reste à faire — mode light** : les 8 tokens de marque (`primary`/`secondary`/`tertiary` + variantes container/on-container) n'ont aucune valeur en light, héritent silencieusement du dark. Tâche reportée explicitement par l'utilisatrice. Prévoir aussi le remplacement des bordures `border-white/X` (quasi invisibles en light).
- **⚠️ `overflow-x: hidden` sur `body` casse silencieusement tout `position: sticky` descendant** : repéré le 02/09 sur l'aside de `ProjectDetailPage.tsx` (ne restait jamais accroché au scroll, aucune erreur console). Cause : le fixup du spec CSS overflow — dès qu'`overflow-x` est non-`visible` sur un élément, `overflow-y` calcule automatiquement à `auto` sur ce même élément, même sans déclaration explicite. `styles.css` déclarait `overflow-x: hidden` sur `html, body` (filet anti-débordement horizontal du 22/07) : `body` devenait donc un second conteneur de scroll aux yeux de `sticky` (dont le *containing block* se résout à la plus proche ancêtre avec un `overflow` calculé non-`visible`, peu importe qu'elle scrolle réellement) — et comme `body` ne déborde jamais de son propre contenu, `sticky` s'y comportait comme `static`. Fix : `overflow-x: hidden` déplacé sur `html` seul (déjà la racine réelle du scroll du document, protège tout aussi bien les descendants via `body`). **Diagnostic qui a fonctionné : scroller réellement et lire `element.getBoundingClientRect().top` à plusieurs paliers de scroll** — `getComputedStyle(el).position === 'sticky'` seul ne suffit pas à confirmer que le sticky fonctionne, il confirme juste que la propriété CSS est bien appliquée, pas son effet réel.

## Base de données / RLS — pièges à ne pas reproduire

- **`security_invoker` sur les vues** : `CREATE OR REPLACE VIEW` ne préserve pas cette option si elle n'est pas re-précisée — retombe en mode `SECURITY DEFINER` implicite (bypass RLS). Toujours `ALTER VIEW ... SET (security_invoker = true)` après un `CREATE OR REPLACE VIEW`, et vérifier avec `select reloptions from pg_class where relname = '...'` (`null` = dangereux). Déjà arrivé une fois sur `projects_catalog_view` (draft visible par anon).
- **Ne jamais supposer qu'un `UPDATE`/`DELETE` a réussi juste parce qu'il n'a pas levé d'erreur** — RLS peut filtrer 0 ligne silencieusement. Toujours vérifier via `RETURNING ... INTO` + check `null`/`GET DIAGNOSTICS` avant de retourner un succès à l'appelant (pattern déjà en place dans `soft_delete_project`, `updateProject*`, `approve/rejectAccessRequest`, `syncProjectTags` — via comparaison du nombre de lignes insérées aux IDs attendus —, et `AccessRequestModal.handleSubmit`/`submitPendingAccessRequest` pour l'`UPDATE user_profiles`).
- **Récursion croisée RLS** : deux policies sur deux tables qui se référencent mutuellement en sous-requête directe déclenchent `42P17`. Passer par des fonctions `SECURITY DEFINER` (comme `get_my_role()`) qui bypassent RLS plutôt qu'une sous-requête brute inter-tables.
- **`REVOKE EXECUTE FROM PUBLIC` ne suffit pas toujours** : les fonctions du schéma `public` peuvent aussi recevoir un `GRANT` explicite à `anon`/`authenticated` (privilège par défaut Supabase sur les nouvelles fonctions), distinct de l'héritage via `PUBLIC`. Un `REVOKE ... FROM anon, authenticated` qui ne cible pas aussi `PUBLIC` (et vice versa) peut ne rien changer en pratique — vérifier avec `has_function_privilege('anon', oid, 'EXECUTE')` après coup, pas seulement relire la migration. Repéré le 15/07 sur `handle_new_user`/`prevent_role_self_update` (hérité de PUBLIC) vs `dispatch_webhook`/`create_access_request_notifications` (GRANT explicite) qui nécessitaient chacun la variante différente.
- **Buckets storage publics (`public: true`) n'ont pas besoin de policy SELECT** sur `storage.objects` : la lecture par URL directe ne passe pas par RLS. Une policy SELECT large (`using (bucket_id = '...')`) autorise en plus le *listing* de tous les fichiers du bucket, inutile et à éviter (advisor Supabase "Public Bucket Allows Listing") — retiré de `project-thumbnails`/`designer-photos` le 15/07.
- **⚠️ Mais aucune policy SELECT du tout casse silencieusement DELETE/UPDATE authentifiés sur ce même bucket** — repéré le 28/09 en vérifiant en direct (appel `DELETE` authentifié, pas juste `tsc`/lecture de code) le flux de suppression d'une image de galerie (`project-gallery`, nouveau bucket) : l'API Storage a besoin d'une requête interne, elle-même soumise à RLS, pour retrouver l'objet avant de le modifier/supprimer. Sans **aucune** policy SELECT (même admin-only), cette recherche échoue et l'opération est bloquée — mais `supabase.storage.from(...).remove([path])` ne renvoie alors **aucune `error`**, juste un tableau vide/partiel (même piège que le pattern RLS-silencieuse déjà documenté ci-dessus pour Postgres, mais côté Storage). Fix : une policy SELECT `to authenticated using (bucket_id = '...' and get_my_role() = 'admin')` (jamais `anon`, pour ne pas réintroduire le problème de listing public) — testé en direct, passe de 403 à 200. Toujours vérifier la `data` retournée par `.remove()` en plus de `error` (cf. `deleteProjectGalleryImage`, `src/lib/storage.ts`). **`project-thumbnails`/`designer-photos` avaient le même trou depuis le 15/07** (leur policy SELECT avait été retirée sans policy admin-only de repli) — confirmé et corrigé le 03/09 (`project_thumbnails_select_admin`/`designer_photos_select_admin`, migration `20260903184843_project_thumbnails_designer_photos_select_admin_for_mutations.sql`, même repro en direct : 403/`data: []` sans la policy → 200/fichier réellement supprimé avec). `deleteProjectThumbnail` (`src/lib/storage.ts`) vérifie désormais `data` en plus de `error`, même pattern que `deleteProjectGalleryImage`. 6 fichiers orphelins trouvés en base et nettoyés à cette occasion (4 dans `project-thumbnails`, 2 dans `designer-photos`) — un seul projet-thumbnail orphelin (`365c6f35.../1783801621557.png`) provenait en fait d'un autre trou, non lié à ce bug : **aucun flux ne supprime l'ancien fichier lors du remplacement d'une miniature/photo pendant une édition** (`deleteProjectThumbnail` n'est appelée que depuis `softDeleteProject`, jamais lors d'un remplacement ; `uploadDesignerPhoto` n'a même pas de fonction de suppression associée) — pas corrigé dans cette session, nouvelle piste si le nettoyage régulier des buckets doit être automatisé.
- **Une policy `INSERT` doit valider TOUTES les colonnes sensibles, pas juste l'`id`** : `user_profiles_insert_trigger_only` ne vérifiait que `id = auth.uid()`, jamais `role` — un utilisateur authentifié aurait pu s'auto-attribuer `role = 'admin'` via un INSERT direct si sa ligne venait à manquer (ex. après un `DELETE` admin, policy `user_profiles_delete_admin`). Corrigé le 15/07 (`AND role = 'pending'` ajouté au `WITH CHECK`). Le nom d'une policy ("trigger_only") n'a aucune valeur de sécurité en soi — seul le `WITH CHECK` compte.
- **`user_profiles_update_own`** (`WITH CHECK (id = auth.uid())`) ne restreint pas non plus la colonne `role` — à elle seule elle laisserait n'importe qui s'auto-promouvoir admin via `UPDATE`. Ce qui bloque réellement ça aujourd'hui est le trigger `trg_prevent_role_self_update` (`BEFORE UPDATE OF role`, fonction `prevent_role_self_update()`) — point de défaillance unique repéré le 15/07 (`RAPPORT_SECURITE.md`) : ne jamais supprimer/modifier ce trigger sans réaliser qu'il est la seule protection sur `role`, la RLS seule ne suffit pas.
- **Vérifier qu'un secret n'a jamais fuité exige de scanner tout l'historique git (`git log --all -p`), pas seulement l'état courant des fichiers.** Repéré le 15/07 : `CRON_SYNC_SECRET` avait été codé en dur dans `sync-notion-veille/index.ts` au commit `d450e43` (13/07), puis déplacé vers `Deno.env.get()` au commit suivant `c43fbea` — mais la valeur elle-même n'avait jamais changé, et ce commit était déjà poussé sur `origin/main`. Un `grep` sur l'état courant du repo ne l'aurait jamais trouvé. Rotation effectuée le 15/07 (nouvelle valeur en Vault via `vault.update_secret`) — la mise à jour du secret Edge Function correspondant (Dashboard ou `supabase secrets set`) reste une étape manuelle, aucun outil MCP disponible pour ça.
- **Une sous-requête corrélée dans un `WITH CHECK` ne peut pas référencer la ligne en cours d'insertion en réutilisant un nom de colonne nu si la sous-requête scanne la même table** : la portée SQL résout la référence vers l'alias le plus proche (celui de la sous-requête), pas vers la nouvelle ligne — silencieusement toujours vrai, pas d'erreur. Repéré le 16/07 sur `contacts_insert_anyone` (1ère version de la limite de fréquence, `c.email = email` devenait `c.email = c.email`) : la policy semblait correcte à la lecture, mais 4 soumissions rapides du même email passaient toutes. Contournement : extraire le calcul dans une fonction `SECURITY DEFINER` qui prend la valeur en paramètre (`contacts_recent_count(email)`) — `SECURITY DEFINER` nécessaire ici aussi car la policy SELECT sous-jacente est admin-only, donc un simple appel en `SECURITY INVOKER` ne verrait aucune ligne pour `anon`/`authenticated` et compterait toujours 0.

## Architecture

- **Routing** : React Router SPA pure (`createBrowserRouter`), plus de TanStack Start/SSR. `src/router.tsx` (routes+loaders), `src/main.tsx` (entry CSR), `index.html` statique avec script `THEME_INIT` inline (seul responsable de la classe `dark`/`light` sur `<html>`, avant tout rendu React).
- **`/` sert directement le profil, plus de redirect (22/07)** : `router.tsx` faisait `loader: () => redirect(...)` vers `/enora-le-turnier` sur `path: "/"` — un aller-retour réseau complet avant même de démarrer le chargement du vrai profil. `/` et `/:slug` pointent désormais tous les deux vers `ProfilePage`/`profileLoader` (même élément, même loader, définis une seule fois sous `SlugLayout`). `profileLoader` accepte maintenant `params.slug` absent (route `/`) en plus de `params.slug === designer.slug` (route `/:slug`) — seul un slug présent mais différent reste une vraie 404. Les liens internes vers `/enora-le-turnier` (Header, Footer, etc.) restent inchangés et fonctionnent toujours, `/` est un raccourci en plus, pas un remplacement.
- **Code-splitting par route (22/07)** : toutes les routes sauf `ProfilePage` (page d'accueil `/:slug`, gardée en import statique — c'est la première page qu'un visiteur charge, pas d'aller-retour réseau supplémentaire à lui ajouter) passent par la prop `lazy` de React Router 7 (`route.lazy: async () => ({ Component, loader })`, pas `React.lazy`+`Suspense` manuel) — chaque page devient son propre chunk Vite chargé à la demande. Avant ça, `router.tsx` important tout statiquement, un visiteur du profil public téléchargeait aussi `AdminPage.tsx` (~2600 lignes) + `react-markdown`/`remark-gfm`/`remark-breaks` (utilisés uniquement par `MarkdownContent`, pages légales/aide) + `date-fns`+locale (Veille Hebdo) dans un unique bundle de 1 002 Ko (281 Ko gzip) — Vite avertissait déjà du seuil 500 Ko dépassé. Exception : `NotFoundPage` reste en import statique dans `router.tsx` (route `*`) malgré le refactor — `RouteError.tsx` l'importe déjà statiquement pour l'`errorElement` racine, un second import dynamique n'aurait donné aucun gain (Vite ne peut pas sortir un module dans son propre chunk s'il est aussi importé statiquement ailleurs, warning `INEFFECTIVE_DYNAMIC_IMPORT` sinon).
- **`@tanstack/react-query` retiré (22/07)** : `RootLayout.tsx` créait un `QueryClient` et enveloppait toute l'app dans `QueryClientProvider`, mais aucun composant n'appelait `useQuery`/`useMutation` nulle part dans le code (toutes les données passent par les loaders React Router, cf. ci-dessus) — poids mort pur au bundle et à l'exécution. Dépendance retirée du `package.json`.
- **`profileLoader` n'appelle plus `getProjects()` (22/07)** : la page profil n'affiche aucune carte projet, seulement un booléen (`hasConfidential`, pour le bouton "Accéder aux projets confidentiels") — `getProjects()` (`select *` sur toute `projects_catalog_view`) était donc un fetch bloquant totalement inutile sur le chemin critique de la page d'accueil. Remplacé par `hasConfidentialProject()` (`src/data/projects.ts`), un `select("id", { count: "exact", head: true }).eq("status", "confidential")` qui ne rapatrie aucune ligne, juste un count via header HTTP.
- **Storage** : bucket `project-thumbnails` (public, écriture admin only) pour les thumbnails projets ; bucket `designer-photos` (même pattern RLS) pour la photo de profil.
- **Versioning** : SemVer dès `main` — `fix:` → PATCH, `feat:` → MINOR (reste en `0.x`, `1.0.0` sera délibéré). Toute fusion sur `main` avec changement utilisateur significatif doit être suivie d'un tag + release GitHub.
- **Navigation mobile (17/07, `< md`/768px)** : `Header.tsx` porte désormais un bloc mobile complet (burger + thème + compte), commun pages publiques et dashboard admin — détail complet (composants, breakpoints, convention "mobile-only") dans `DESIGN.md` section "Navigation mobile". `AdminSidebar` passée en `hidden md:flex` (remplacée par `AdminMobileBottomNav` sur mobile, Paramètres déplacé dans la feuille compte sous "Préférences") — ne jamais réintroduire l'ancienne sidebar icône-seule en mobile. `useThemeMode` (`src/hooks/useThemeMode.ts`) est la seule source de vérité pour le thème, partagée entre `ThemeToggle` (desktop) et `MobileThemeSheet` — ne pas dupliquer l'état thème ailleurs.
- **Overlays et filtres mobile (17/07)** : tiroirs latéraux (`ProjectDrawer`, asides en lecture seule d'`AdminPage`) et footers de boutons (`ProjectDrawer`, `AccessRequestModal`, confirmations `AdminPage`) responsive sous `md` — détail (classes exactes, avant/après) dans `DESIGN.md` section "Overlays et filtres mobile". `FilterBar`/`AdminFilterBar` : pills en scroll horizontal (`.scrollbar-hide`, `styles.css`) + panneau "Filtrer" en `SlideSheet from="left"` sous `md` au lieu de l'expand inline desktop — `SlideSheet` a gagné une prop `className` pour ce pattern (variante mobile-only rendue en parallèle d'une variante desktop, gating CSS `md:hidden`/`hidden md:flex`, pas de media query JS).
